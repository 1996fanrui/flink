# D1 — 单次 channelIOExecutor submit + drainHandoff

## 设计期望

recovery 期间 `channelIOExecutor.execute(...)` 在主路径上只调用一次；runnable 内连续执行
`filter → drainHandoff.get() → drain → close`。`drainHandoff.get()` 必须能响应
`InterruptedException`。filter-off 路径下 runnable 跑完 filter 即 return，不进入 wait。
shutdown 行（既有 `channelIOExecutor.shutdown()`）保持 master 原样。

设计来源：`requirements/38544/simplify_approach/overview.md` §2、§7；`unspiller.md` §1；
`task_breakdown.md` Phase 4 接线条目。

## 符合预期

- `StreamTask.java:916` 是 main source 中唯一的 `channelIOExecutor.execute(...)`
  调用点（已 grep 全部 main java，仅一处）。
- `StreamTask.java:918-969` runnable 内严格按 `filter (readInputData) → drainHandoff.get()
  → spillReader.drain() → spillReader.close()` 线性执行，无二次 submit。
- `StreamTask.java:944-952` 的 `drainHandoff.get()` 分别捕获 `InterruptedException`（恢复
  中断标志后退出）与 `ExecutionException`（report async exception 后退出），符合 checklist
  对 InterruptedException 可响应的要求。
- `StreamTask.java:914-915` 在 feature-off 时 `drainHandoff = null`；
  `StreamTask.java:939-941` 在 runnable 内进入 wait 前先判 null 直接 return，filter-off
  路径不进 `drainHandoff.get()`，与 master 行为对齐。
- `StreamTask.java:863` 的 shutdown 行未发生条件化或延后改动，与 checklist 要求 "shutdown
  line 862 任何改动需 review 动机" 一致。
- 退出路径完整：(a) filter 抛错 → `completeExceptionally(e)` (`:935`)；(b) handoff 正常
  → `complete(spillReader)` / `complete(null)` (`:1075,:1085`)；(c) build 抛错 →
  `completeExceptionally(t)` (`:1087`)；(d) `allConverted` 错误分支 →
  `completeExceptionally(err)` (`:1030`)。drain 与 close 各自包在 try/finally 中
  (`:956-968`)，close 异常不会吞 drain 异常。
