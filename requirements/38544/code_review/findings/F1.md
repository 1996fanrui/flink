# F1. 3-step 调度器入口（仅两处 UC 入口）

## 设计期望

仅在两处 UC barrier 入口调用 `ChannelState.onCheckpointStartedForAllInputs`：
- `AlternatingWaitingForFirstBarrierUnaligned.barrierReceived`（从 UC 入口）
- `AlternatingCollectingBarriers.barrierReceived`（aligned 切 UC）

不允许在其他 trigger 入口（aligned 主路径、abort、unaligned 后续 barrier 等）调用；
反过来这两处必须调，否则 cpId 永远走不了 3-step。
dispatcher 是任务级别一次性调用，无外层 `if (filter-on)` guard。

## 符合预期

1. 全仓 `grep -rn "onCheckpointStartedForAllInputs"` 在 main 中仅 3 处命中：dispatcher 定义 1 处 + 调用 2 处，调用点全部位于 alternating UC barrier handler，无补充调用、无 aligned/abort 路径泄漏。
2. dispatcher 内部 (ChannelState.java:162-169) 顺序 Step1 → 每输入 `checkpointStarted` → Step3，与设计一致；无外层 `if (filter-on)` guard，依赖 `RecoveryCheckpointTrigger.NO_OP` 与 writer null 收敛。
3. dispatcher 在 `barrier.getId()` 入口取一次 cpId（line 160），任务级一次性调用 trigger 与 writer，未在 per-gate 循环里重复。
4. abort 路径（AlternatingWaitingForFirstBarrierUnaligned.java:90-92、AbstractAlternatingAlignedBarrierHandlerState.java:85-87）只走 `stopCheckpoint()`/`finishCheckpoint()`，未 hook dispatcher。
5. 全仓 main 中 `input.checkpointStarted(` 唯一调用点在 ChannelState.java:166，确认 master 既有的 per-gate `checkpointStarted` 外层循环已被 dispatcher 收编、未残留重复调用。

## 不符合预期

- `AlternatingCollectingBarriers.java:49`：dispatcher 实际 hook 在 `alignedCheckpointTimeout` 而非 design 文档 (`task_breakdown.md:97`、`coordination.md:108`) 明确点名的 `AlternatingCollectingBarriers.barrierReceived`。功能上等价（`AbstractAlternatingAlignedBarrierHandlerState.barrierReceived:54-55,71-72` 把 UC 切换委派给 `alignedCheckpointTimeout`，且 `endOfPartitionReceived` 通过 line 74 同样进入此方法），但位置与设计文字不一致，属于 minor 命名偏差。

## 总评
