# E3. recoveredBuffers 锁复用 + 锁顺序

## 设计期望

- Remote 复用 master 既有 `synchronized(receivedBuffers)`，同一个 monitor 同时保护 `receivedBuffers` 与新增 `recoveredBuffers` / `allRecoveredBuffersDelivered`；Local 由于 master 无 `receivedBuffers`，使用 `synchronized(recoveredBuffers)` 自身做 monitor。
- 不引入第三个 lock 对象（channel 上只有 master 既有的 `requestLock` 等 + 新的字段做 monitor，无单独 `Object lock`）。
- 全局锁顺序：`SpillFileReader.lock` → channel-internal queue monitor（drain delivery 与 Step 1 barrier insert 都按这个方向）。
- `onRecoveredStateBuffer` 内进入 channel monitor 时调用方必须已持 `SpillFileReader.lock`（migration path 例外）。
- monitor 内 critical section 不允许 park / IO / sleep；外侧 `notifyChannelNonEmpty()` 要走在 monitor 释放后。

## 符合预期

- `LocalInputChannel` 用 `synchronized(recoveredBuffers)` 作为唯一新增 monitor，未引入 `private final Object lock`；唯一独立 `Object requestLock`（`LocalInputChannel.java:73`）是 master 既有，仅守 `requestSubpartitions` 路径。
- `RemoteInputChannel` 复用 `synchronized(receivedBuffers)`，所有新字段 `recoveredBuffers`/`allRecoveredBuffersDelivered` 都标 `@GuardedBy("receivedBuffers")`（`RemoteInputChannel.java:132,146`）；全文未见 `synchronized(recoveredBuffers)`，未引入新 monitor。
- `onRecoveredStateBuffer` 实现（`LocalInputChannel.java:167-181`、`RemoteInputChannel.java:225-239`）进入 channel monitor 期间仅做 enqueue + `wasEmpty` 计算，`notifyChannelNonEmpty()` 在 monitor 释放后调用，不在 monitor 内做 IO / park。
- Drain critical section（`SpillFileReader.java:126-131`）按 `SpillFileReader.lock` → `ch.onRecoveredStateBuffer(buf)`（内部再取 channel monitor）的方向，符合 `outer→inner` 锁序；snapshotAndInsertBarriers（`SpillFileReader.java:147-169`）走同一方向。
- `finishReadRecoveredState`（`LocalInputChannel.java:190-194`、`RemoteInputChannel.java:248-252`）只进 channel monitor，不持 `SpillFileReader.lock`，符合 end-of-drain 例外。
- `getNextBuffer` / `checkpointStarted` / `releaseAllResources`（`LocalInputChannel.java:381-403,676-685`、`RemoteInputChannel.java:330-376,854-890,482-493`）的 recovery 读路径只持 channel monitor，无反向锁请求，无锁内 IO / 阻塞。
- `SingleInputGate.convertRecoveredInputChannels`（`SingleInputGate.java:410-421`）显式注释要求 `receivedBuffers` → `inputChannelsWithData` 的统一方向，进一步避免与 `onRecoveredStateBuffer` 形成反向锁链。

## 不符合预期

无。

## 总评

PASS — Remote / Local 锁复用与 `SpillFileReader.lock → channel monitor` 锁序在所有 recovery 路径上一致，且 monitor 内未见阻塞动作。
