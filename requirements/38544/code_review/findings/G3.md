# G3. Future / latch / counter 在所有路径一致

## 设计期望

跨线程同步对象（`drainHandoff` / `bufferFilteringCompleteFuture` / `conversionDoneFutures[i]` / `allRecoveredBuffersDelivered` / `stateConsumedFuture` / `SpillFile.refCount`）在所有可达终态都保持一致：漏完成 → hang；多次完成或多次 release → 静默错误 / use-after-free。每个 acquire 必须配 release（成功 + 异常）。

## 符合预期

- `drainHandoff` 三条退出路径均显式 complete：成功 `complete(spillReader)` / 无 spillFile `complete(null)`（StreamTask.java:1075, 1085）、handoff catch `completeExceptionally(t)`（:1087）、filter 抛 `completeExceptionally(e)`（:935）、conversion err `completeExceptionally(err)`（:1030）。
- `DiskSnapshot.close()` 显式 idempotent（DiskSnapshot.java:168-176，`closed` flag + 单次 `spillFile.release()`）。
- `replayInputDataFromSpill` 的 discard 回调 `chunks.close()` 与 writer finally `chunks.close()` 同源（ChannelStateWriteRequest.java:280；ChannelStateCheckpointWriter.java:176, 200）；多次 close idempotent 注释也在 ChannelStateWriterImpl.java:266 显式声明。
- `SpillFile.deleteAllSegments` 通过 `cleanedUp` AtomicBoolean CAS 保证仅执行一次（SpillFile.java:287, 306），`release()` 与 forced `close()` 共享 CAS。
- `conversionDone` 在 success / 异常两条路径都显式 complete（StreamTask.java:992, 994）。

## 不符合预期

- `flink-runtime/src/main/java/org/apache/flink/runtime/checkpoint/channel/RecoveredChannelStateHandler.java:347-373` close() 顺序为：`spillFileWriter.close()`（:354）→ `filterOutputPooledBuffer.recycleBuffer()`（:361）→ `inputGate.finishReadRecoveredState()`（:365-367，完成 `bufferFilteringCompleteFuture`）。前两步若抛异常，第三步永不执行 → `bufferFilteringCompleteFuture` 永不完成 → `allRecoveredFuture` 永不完成 → mailbox 永不 suspend，task hang。设计 G3 要求 future 在所有终态完成；此处违反。
- `flink-runtime/src/main/java/org/apache/flink/streaming/runtime/tasks/StreamTask.java:920-936, 1030, 1095-1103` 双 release 路径：当 filter 抛但 `stateHandler.close()` 中 :354 / :361 之前的步骤已完成 finishReadRecoveredState（:365）时，`bufferFilteringCompleteFuture` 已 done → `requestPartitionsTrigger.thenRun` 触发 conversion → 成功后 `allConverted.whenComplete` 的成功分支 :1033 调度 `handoffSpillReaderToDrain`，其 finally :1097 第二次 `spillFile.release()`；而 :930 已经 release 过一次 → SpillFile.refCount 下溢到 0 触发 `deleteAllSegments`，drain reader 后续构造时 `acquire()` 已无法挽回 cleanedUp CAS。SpillFile 提前删段，drain 路径上 segment 文件丢失。
- `flink-runtime/src/main/java/org/apache/flink/runtime/checkpoint/channel/SpillFileReader.java:147-169` `snapshotAndInsertBarriers` 在 `synchronized(lock)` 内先 `spillFile.acquire()` :163，随后 for-loop 调 `EventSerializer.toBuffer(new RecoveryCheckpointBarrier(...), false)` :166-167。`toBuffer` 抛异常时（如 ByteBuffer/Memory 异常）：acquire 已生效，但方法未返回 `DiskSnapshot`，调用方（ChannelState.java:172 finally 只对返回的 snap 调 close）无从释放该 grant → SpillFile.refCount 永远不归零 → 段永不删除（资源泄漏）。同时部分 channel 已收到 barrier，其余没收到 → checkpointStarted Step 2 在没收到 barrier 的 channel 走 fail-loud throw（F4），整体状态不一致。
- `flink-runtime/src/main/java/org/apache/flink/runtime/io/network/partition/consumer/RecoveredInputChannel.java:219-223` `finishReadRecoveredState` 在 `synchronized(receivedBuffers)` 内先 `EventSerializer.toBuffer(EndOfInputChannelStateEvent.INSTANCE, false)`（:220-221）再 `bufferFilteringCompleteFuture.complete(null)`（:222）。`toBuffer` 抛时 future 永不完成 → 与 close() 路径同样导致 task hang。
- `flink-runtime/src/main/java/org/apache/flink/runtime/io/network/partition/consumer/LocalInputChannel.java:189-194` 与 `RemoteInputChannel.java:247-252` 的 `finishReadRecoveredState` 只翻转 `allRecoveredBuffersDelivered` 标志，**未完成任何 `stateConsumedFuture`**。但 `RecoverableInputChannel.java:61-62` 接口契约明确写："The channel completes `stateConsumedFuture` once both this flag is `true` AND `recoveredBuffers` is empty"。且 `SingleInputGate.getStateConsumedFuture`（:321-332）只收集 `RecoveredInputChannel` 类型，转换后无任何 future 表达 "physical channel recovery fully consumed" → 接口注释 vs 实现 / 设计 vs 代码偏离；filter-on path 因为 `requestPartitionsTrigger` 改用 `getBufferFilteringCompleteFuture` 当前不触发 hang，但接口语义已破。
- `flink-runtime/src/main/java/org/apache/flink/runtime/checkpoint/channel/SpillFileReader.java:99-139` `drain()` 无 try/finally 兜底；(C) 块或 (B) 读盘抛错时，循环外的 `(D) finishReadRecoveredState` 不会对任何 channel 执行。下游观察者依赖 `allRecoveredBuffersDelivered && recoveredBuffers.isEmpty()` 判定 inRecovery 终态（input_channel.md §3.7）；该标志永不为 true → channel.inRecovery 永远为 true → checkpointStarted 永远进 in-recovery 分支但找不到 barrier，且 `getNextBuffer` 永远屏蔽 upstream data。

## 总评

FAIL — 多个 future / refCount 在异常路径上存在漏完成或双 release 风险（RecoveredChannelStateHandler.close() 部分失败 → bufferFilteringCompleteFuture hang；filter-throw + close-partial-success → SpillFile 双 release；snapshotAndInsertBarriers EventSerializer 抛 → 引用泄漏 + 部分 channel 状态不一致；drain 抛 → allRecoveredBuffersDelivered 永不翻转），且 `stateConsumedFuture` 在 Local/Remote 上未按接口契约实现。
