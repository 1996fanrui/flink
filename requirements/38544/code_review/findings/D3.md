# D3. Conversion → drain 严格串行 — Findings

## 设计期望

filter → conversion → drain 严格串行；drain 真正开始时所有 channel 已是物理 channel；filter 阶段 gate 内 channel 仍为 `RecoveredInputChannel`；filter 内部不允许触发 conversion；不允许"先 drain 一部分、再 conversion、再 drain"的交错；`requestPartitions` 不允许延后到 drain 完。时序链：`bufferFilteringCompleteFuture` → `requestPartitions` mail → `conversionDoneFutures` → handoff 构造 `SpillFileReader` → `drainHandoff` → `drain`。

## 符合预期

- `channelIOExecutor.execute` 在 recovery 流程中只 1 处（`StreamTask.java:916`），runnable 内连续 filter (line 919) → `drainHandoff.get()` (line 944) → `spillReader.drain()` (line 957)，I/O 线程在 drain 前在 `drainHandoff.get()` 阻塞，串行点明确（`StreamTask.java:909-969`）。
- 时序链端到端可验：filter 结束 → `RecoveredChannelStateHandler.close` 冻结 spillFile 再触发各 gate `finishReadRecoveredState` (`RecoveredChannelStateHandler.java:354-366`) → channel `finishReadRecoveredState` 完成 `bufferFilteringCompleteFuture` (`RecoveredInputChannel.java:219-223`) → gate `getBufferFilteringCompleteFuture` resolve (`SingleInputGate.java:345-356`) → `thenRun` 投递 `requestPartitions` 邮件到 mailbox (`StreamTask.java:986-998`) → `requestPartitions` 调 `convertRecoveredInputChannels` (`SingleInputGate.java:379`) 后 `conversionDone.complete(null)` (`StreamTask.java:992`) → `allConverted.whenComplete` 投递 `handoffSpillReaderToDrain` mailbox 邮件 (`StreamTask.java:1015-1037`) → `drainHandoff.complete(reader)` (`StreamTask.java:1085`) → I/O 线程被唤醒后跑 `drain()`。
- `convertRecoveredInputChannels` 唯一调用点为 `SingleInputGate.requestPartitions` (`SingleInputGate.java:379`)；`requestPartitions()` 在 production 也仅由 `StreamTask.java:991` 的 mailbox mail 调用。filter 路径 (`RecoveredChannelStateHandler.recover` / `readInputData`) 不触发 conversion。
- `sourceChannels` 在 `restoreStateAndGates` 直接同步调用 `collectRecoveredChannels` (`StreamTask.java:1010-1011`)，时机在 `mailboxProcessor.runMailboxLoop()` (`StreamTask.java:849`) 启动之前；任何 conversion mail 都还没被 mailbox 处理，因此抓到的全是 `RecoveredInputChannel`。
- `physicalChannels` 在 `handoffSpillReaderToDrain` (`StreamTask.java:1078-1079`) 内通过 `collectPhysicalChannels` 收集；该方法在 `allConverted` 完成之后通过 `mainMailboxExecutor.execute` 投递，因此当 task 线程执行时所有 gate 已完成 conversion，channel 已是物理 `LocalInputChannel`/`RemoteInputChannel`。
- `SpillFileReader.drain` (`SpillFileReader.java:99-139`) 持有的 `allChannels` 来自构造时传入的 `physicalChannels`，无任何运行时 cast 或重新 lookup，符合"drain 时 allChannels 必须都是物理 channel"。
- `requestPartitions` 不会被延后到 drain 之后：它在 `bufferFilteringCompleteFuture` 触发后立即排到 mailbox（`StreamTask.java:986`），而 `handoffSpillReaderToDrain` 也走 mailbox 排队，两者顺序由 `conversionDoneFutures` + `allConverted` 强制（`StreamTask.java:1012-1038`）。
- 无"drain 一部分、conversion、drain"交错：drain 是 `SpillFileReader.drain` 内单次 for-loop（`SpillFileReader.java:100-133`），不接受外部分段调度；I/O 线程进入 drain 后只通过单一线程顺序遍历直到结束（D 步），中间不返回 mailbox。
- handoff 异常路径同样维持串行约束：`allConverted` err 分支 (`StreamTask.java:1017-1031`) 释放 producer grant + `drainHandoff.completeExceptionally`，I/O 线程在 `drainHandoff.get()` 命中 `ExecutionException` 后直接 return，不进入 drain（`StreamTask.java:948-951`）。

## 总评

PASS — 当前实现通过 single-submit runnable + `drainHandoff` 等待 + `allConverted` → mailbox handoff 的链路，严格保证 filter→conversion→drain 顺序且无交错；`sourceChannels` / `physicalChannels` 两次采集点的时序与 mailbox 串行性匹配。
