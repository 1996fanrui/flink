# F4 — checkpointStarted 必须找到 cpId-matched barrier（防御性）

## 设计期望

- `coordination.md` §3.3 / `input_channel.md` §3.8 / `review_checklist.md` F4 共同约束：当 channel 处于 in-recovery 分支（`!allRecoveredBuffersDelivered || !recoveredBuffers.isEmpty()`）时，`checkpointStarted` 必须在 `recoveredBuffers` 中找到与 `barrier.getId()` 匹配的 `RecoveryCheckpointBarrier` sentinel，并 `it.remove()` 它。
- 关键防御性约束：
  1. 走到队列尾仍未找到匹配 barrier 必须 throw（不能 silent return）。
  2. 队列为空但 `inRecovery == true`（Step 1 已插过 barrier）同样必须 throw。
  3. 找到了 sentinel 但 cpId 不匹配 → 不能误移除；继续扫描；全无匹配 → throw。
  4. 必须用真正会触发的异常路径（throw），禁止 `assert`（assert default-off）。
  5. 不允许 "找不到当作空 retained 喂 writer" 的 silent fallback（会让 checkpoint 静默丢数据）。

## 已 review 代码位置

- `flink-runtime/src/main/java/org/apache/flink/runtime/io/network/partition/consumer/LocalInputChannel.java:200-265`（`checkpointStarted` + `collectPreRecoveryBarrier` + `isRecoveryCheckpointBarrier`）
- `flink-runtime/src/main/java/org/apache/flink/runtime/io/network/partition/consumer/RemoteInputChannel.java:854-931`（同上三函数 + 互斥分支）
- `flink-runtime/src/main/java/org/apache/flink/runtime/checkpoint/channel/RecoveryCheckpointBarrier.java:37-77`（sentinel 定义，equality 包含 cpId）
- `flink-runtime/src/main/java/org/apache/flink/runtime/checkpoint/channel/SpillFileReader.java:160-170`（Step 1 插入 barrier 的位置，确认每 channel 都会插）

## 符合预期

- `LocalInputChannel.collectPreRecoveryBarrier`（`LocalInputChannel.java:243-247`）与 `RemoteInputChannel.collectPreRecoveryBarrier`（`RemoteInputChannel.java:909-913`）：找到 cpId 匹配的 barrier 时 `it.remove()` 真移除 + `b.recycleBuffer()` 回收并 `return retained`（早退，不会再追加后续 buffer 到 retained）。
- `isRecoveryCheckpointBarrier`（`LocalInputChannel.java:255-265` / `RemoteInputChannel.java:921-931`）只对 `!isBuffer()` 的 event buffer 反序列化，并强制 `getCheckpointId() == checkpointId` 才认作匹配 → 不匹配的 sentinel 不会被误移除，循环会继续到下一个候选；同时 `setReaderIndex(0)` 把 reader index 复原，保证后续可重读。
- `checkpointStarted` 在 `inRecovery == true` 时只走 in-recovery 分支（`LocalInputChannel.java:206-207`、`RemoteInputChannel.java:858-865`），不会回退到 master 分支，符合 F3 互斥要求。
- `RecoveryCheckpointBarrier.equals`（`RecoveryCheckpointBarrier.java:69-72`）以 `checkpointId` 区分，cpId 不同的 sentinel 在语义上互不影响。

## 不符合预期

- `LocalInputChannel.java:252` — `collectPreRecoveryBarrier` 走到 `while` 出口（队列扫尽未找到匹配 barrier）时 `return retained;` silent fallback；调用方 `checkpointStarted` 拿到不完整的 retained list 直接喂给 `channelStatePersister.startPersisting`（`LocalInputChannel.java:218`），违反 F4 "找不到必须 throw" 的强约束。该路径会同时覆盖三个 fail-loud 子条款：(a) 队列尾无匹配；(b) `inRecovery==true` 但 queue 当前为空（while 不进入即落入同一 fallback）；(c) 队列里只有不匹配 cpId 的旧 sentinel —— 三种 bug 全部静默为 "空 retained"。
- `RemoteInputChannel.java:918` — 同上，`collectPreRecoveryBarrier` 走到出口时 `return retained;` silent fallback；调用方 `checkpointStarted`（`RemoteInputChannel.java:865`）继续把不完整结果传给 `startPersisting`（`RemoteInputChannel.java:882`）。
- `LocalInputChannel.java:238` / `RemoteInputChannel.java:904` — 方法签名仅 `throws IOException`，没有为 "barrier not found" 设计专门的异常类型/分支；当前实现连 `assert` 都没有（assert 是默认关闭的，按 F4 也不允许），属于完全无防御的 silent fallback。
- 设计文档（`input_channel.md` §3.8 第 130-131 行 pseudocode `it.remove(); break;`）与 `coordination.md` §7 "Defensive invariants" 都明确点名 `channel.checkpointStarted` 必须 fail-loud；当前实现违反该 invariant。

## 总评

FAIL — `LocalInputChannel` 与 `RemoteInputChannel` 的 `collectPreRecoveryBarrier` 在 in-recovery 分支找不到 cpId-matched `RecoveryCheckpointBarrier` 时直接 silent `return retained`，违反 F4 / coordination §7 强制的 fail-loud 约束，会让"Step 1 漏插 barrier"或"cpId 错配"之类的 bug 静默退化为 checkpoint 数据丢失。
