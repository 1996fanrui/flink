# E6. stateConsumedFuture 精确完成条件

## 设计期望

依据 `input_channel.md` §3.7 与 `overview.md` 第 67 行 / `RecoverableInputChannel` 接口 javadoc：

- `stateConsumedFuture` 应由 channel 自身在 `allRecoveredBuffersDelivered == true && recoveredBuffers.isEmpty()` 两者均成立时完成。
- 触发位点仅两条：
  (a) `finishReadRecoveredState()` 运行时 `recoveredBuffers` 已空；
  (b) consumer 在 flag 已为 true 时 poll 走最后一条。
- 禁止 EOICS sentinel 入 `recoveredBuffers` 触发完成。
- 禁止其他位置（task close / bootstrap 等）兜底完成。
- 应让物理 channel（Local / Remote）也参与 `stateConsumedFuture` 完成，因为 drain 是在 conversion 之后给它们投递 buffer 的（参见 `overview.md` §2 Timeline）。

## 符合预期

- `RecoveredInputChannel.stateConsumedFuture` 仅在 `RecoveredInputChannel` 内部声明并且只有 1 处 `complete(null)`（line 244），符合 "幂等触发，第一次真值决定" 的语义。
- 没有其他 "兜底" complete 入口（task close / bootstrap 等）—— 全仓 grep `stateConsumedFuture.complete` 只出现在 `RecoveredInputChannel.java:244` 一处。
- feature-off 路径仍走 master 既有 EOICS 触发机制（`RecoveredInputChannel.toInputChannel` 在 line 117-120 强制要求 `stateConsumedFuture.isDone()`），未引入新位点。

## 不符合预期

- `RecoverableInputChannel.java:57-66` 接口契约写明 "The channel completes `stateConsumedFuture` once both this flag is true AND `recoveredBuffers` is empty"；但 `LocalInputChannel.java:190-194` 与 `RemoteInputChannel.java:248-252` 的 `finishReadRecoveredState()` **只翻 flag，没有 complete 任何 `stateConsumedFuture`**，且这两类 channel 也 **没有 `stateConsumedFuture` 字段**（见 `LocalInputChannel.java:69-122` 字段列表与 `RemoteInputChannel.java:130-156`）。设计 §3.7 列的两条触发位 (a) `finishReadRecoveredState` 跑到时 queue 已空、(b) consumer poll 走最后一条 flag 已为 true —— 在 Local/Remote 路径**两条都未实现**。

- `RecoveredInputChannel.java:219-223` `finishReadRecoveredState` 仍向 `receivedBuffers` 插入 `EndOfInputChannelStateEvent` 并经 `getNextRecoveredStateBuffer` (line 241-245) 消费时才 `stateConsumedFuture.complete(null)`。设计 §3.7 明文 "No EOICS sentinel is inserted into the queue" 仅适用于新 `recoveredBuffers` 路径；该 EOICS 触发位本身保留无问题，但 `RecoveredInputChannel.toInputChannel` (line 124-141) 把含 EOICS 的 `remainingBuffers` 全量 push 到物理 channel `recoveredBuffers` 后，**物理 channel 的 `getNextBuffer` 没有任何 EOICS 检测**（`LocalInputChannel.java:381-467` 与 `RemoteInputChannel.java:329-377` 均无 `isEndOfInputChannelStateEvent` 分支），EOICS 会作为非 data event 流向 operator chain，**对应的 stateConsumedFuture 永远停留在未完成态**。当 feature on（`StreamTask.java:978-980` 走 `getBufferFilteringCompleteFuture` 不等 `stateConsumedFuture`）时这不阻塞流程；但接口契约与设计文档承诺被破坏。

- `SingleInputGate.java:321-332` `getStateConsumedFuture` 仅迭代 `RecoveredInputChannel` 实例收集 future。conversion 完成后 channels 全部替换为 Local/Remote 物理 channel（line 415-430），`getStateConsumedFuture` 在 conversion 后调用会返回 `CompletableFuture.allOf(empty)`（即立即 done）。**这意味着 "channel 自身完成 stateConsumedFuture" 即使被实现也无法被 gate 收集到**——这是更深层的契约脱节：要么 gate 收集层需要扩展到 `RecoverableInputChannel`，要么设计 §3.7 的 "channel 自身完成 stateConsumedFuture" 描述要改写。

## 总评

FAIL —— `RecoverableInputChannel` 接口契约与 `input_channel.md` §3.7 的承诺均未落地：Local/Remote channel 没有 `stateConsumedFuture` 字段也没有完成位，设计列的两条触发位 (a)(b) 在物理 channel 路径完全缺失。
