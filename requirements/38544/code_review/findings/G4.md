# G4 — Feature-off 路径零 overhead

## 设计期望

feature-off (`checkpointingDuringRecoveryEnabled=false`) 时整个流程等同 master：
- `RecoveredChannelStateHandler` 不构造 `SpillFileWriter`（字段保持 null）；
- `getProducedSpillFile()` 返回 null → handoff 早 return → `drainHandoff.complete(null)` → I/O 线程拿 null 直接 return；
- `RecoveryCheckpointTrigger` 默认 no-op + `addInputDataFromSpill` 空 snap no-op，使调度器层无外层 `if (filter-on)`；
- `channelIOExecutor` 行为与 master 一致，不跑 wait-blocking runnable。

## 符合预期

- `RecoveredChannelStateHandler.recover` (`RecoveredChannelStateHandler.java:213-223`) feature-off 走 `filteringHandler == null` 分支，直接 `channel.onRecoveredStateBuffer(...)`，不进入 `ensureSpillFileWriter`；`spillFileWriter` 与 `producedSpillFile` 字段保持 null。
- `SequentialChannelStateReaderImpl.readInputData` (`SequentialChannelStateReaderImpl.java:76-79`) feature-off 时 `filteringHandler = null`，向 handler 注入 null filter，杜绝 spill 路径。
- `StreamTask.restoreStateAndGates` 提交的 runnable (`StreamTask.java:914-969`) feature-off 时 `drainHandoff == null` (line 915)，runnable 在 `readInputData` 完成后于 line 939-941 直接 return，不进入 `drainHandoff.get()` 等待，等价于 master 的单次 submit。
- `StreamTask.restoreStateAndGates` (`StreamTask.java:1009`) 用 `if (checkpointingDuringRecoveryEnabled)` 包裹整段 conversion → handoff 链路，feature-off 时不创建 `allConverted.whenComplete` 回调、不调用 `handoffSpillReaderToDrain`、不构造 `SpillFileReader`。
- `RecoveryCheckpointTrigger.NO_OP` (`RecoveryCheckpointTrigger.java:63`) lambda 返回 `DiskSnapshot.empty()`，不持锁、不插 barrier。
- `DiskSnapshot.empty()` (`DiskSnapshot.java:79-89, 109-116`) 复用 `EMPTY_INSTANCE` 单例，`hasNext()` 直接 `false`，`close()` 走 line 173 `if (spillFile != null)` 后是 no-op。
- `ChannelStateWriterImpl.addInputDataFromSpill` (`ChannelStateWriterImpl.java:245-256`) 空 snap 走 short-circuit：`chunks.hasNext()` 为 false 直接关闭迭代器、不入队 writer 线程。`NoOpChannelStateWriter.addInputDataFromSpill` (`ChannelStateWriter.java:245-252`) 同样仅关闭迭代器。
- `ChannelState.onCheckpointStartedForAllInputs` (`ChannelState.java:158-184`) 调度器层无外层 `if (filterEnabled)`，依赖 trigger / writer 的 NO_OP 收敛。
- `SingleCheckpointBarrierHandler.aligned` (`SingleCheckpointBarrierHandler.java:155-178`) aligned-only 路径用 `new ChannelState(inputs)` 单参构造器，落到 `ChannelState.java:76-78` 的 `NO_OP / NO_OP` 形式，与 master 完全等价。
- `InputProcessorUtil` 的 `lazyTrigger` (`InputProcessorUtil.java:130-135`) 在 `recoveryCheckpointTriggerSupplier.get()` 返回 null 时回退到 `RecoveryCheckpointTrigger.NO_OP`；feature-off `StreamTask.recoveryCheckpointTrigger` 始终为 null (line 321, 1084 永远不会执行)。
- `RecoveredInputChannel.toInputChannel` (`RecoveredInputChannel.java:136-147`) feature-off 仍走"逐 buffer onRecoveredStateBuffer + 末尾 finishReadRecoveredState"迁移，使物理 channel 的 `allRecoveredBuffersDelivered` 在投入使用前已 = true，让随后 `getNextBuffer` 的 inRecovery 判定快速短路。
- `setCheckpointingDuringRecoveryEnabled` (`SingleInputGate.java:335-342`) 是 `volatile boolean` 单字段，feature-off 仅写一次 false（默认值）。

## 不符合预期

- `LocalInputChannel.java:381-403`：feature-off 时 `getNextBuffer()` 每次仍进入 `synchronized (recoveredBuffers)` 读取 `inRecovery` 谓词。master 版（`git show master:.../LocalInputChannel.java` line 233-260）的 `getNextBuffer` 无任何同步开销。recovery 完成后 `allRecoveredBuffersDelivered=true && recoveredBuffers.isEmpty()` 永远成立，但**每条记录仍付 monitor enter/exit**，不满足"零 overhead"。
- `LocalInputChannel.java:200-225`：feature-off `checkpointStarted` 进入 `synchronized (recoveredBuffers)` 块、构造 `toPersist` list、判断 `inRecovery`。master 版仅 `channelStatePersister.startPersisting(barrier.getId(), Collections.emptyList())` 一行（`git show master:.../LocalInputChannel.java` line 114-116），无同步、无分配。
- `RemoteInputChannel.java:336-339`：feature-off `getNextBuffer()` 多出第一段 `synchronized (receivedBuffers) { inRecovery = ... }`，与第二段 `synchronized (receivedBuffers)` 主路径属两次独立 monitor acquire。recovery 完成后 inRecovery 永远 false，但每条记录额外 acquire 一次同 monitor，可能影响热路径吞吐。
- `RemoteInputChannel.java:857-883`：feature-off `checkpointStarted` 在原本就持 `synchronized(receivedBuffers)` 的主路径前新增 `inRecovery` 计算 + `assert recoveredBuffers.isEmpty()`，相对 master 是新增分支判断（每次 checkpoint 一次，低频，但仍不为零）。

## 总评

PASS WITH MINOR：handler / StreamTask / 调度器 / writer 层 feature-off 路径全部以 null + NO_OP 单例收敛，未引入分支或线程；但 `LocalInputChannel.getNextBuffer` 在 feature-off 仍持有 `synchronized(recoveredBuffers)`，把原本无锁的本地热路径改为每条记录一次 monitor acquire，违反"零 overhead"的设计期望。
