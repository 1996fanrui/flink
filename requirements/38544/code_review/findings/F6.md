# F6. Step 3 — addInputDataFromSpill 写入正确性

## 设计期望

- writer 端按 `chunk.channelInfo` 分派到对应 channel 的 input-channel state handle，不靠 chunk 顺序推断 channel。
- 跳过 `entryPos < startPos`：按 `(segmentIndex, offset)` 字典序，先 segmentIndex 再 offset。
- 异步 writer 在独立线程上 demux，不依赖 task thread 活着；写入失败也能通过 result future 异常完成。
- DiskSnapshot 持有的 SpillFile grant 在所有路径必须释放：成功（writer finally）、abort/cancel（request discardAction）、submit 失败（cancel 调度）、empty 提前返回（inline close）、dispatcher 同步异常（ChannelState finally）。
- 空 snap 在 writer 入口短路返回，不提交 writer 线程任务。

## 符合预期

- demux 按 `chunk.channelInfo` 路由：`ChannelStateCheckpointWriter.writeInputFromSpill:193-197` 用 `pendingResult.getInputChannelOffsets().computeIfAbsent(chunk.channelInfo, ...)`，与 chunk 出现顺序无关；最终在 `ChannelStatePendingResult.complete:128-132` 按 `Map<InputChannelInfo, StateContentMetaInfo>` 逐 channel 产出一份 `InputChannelStateHandle`。
- 跳过 `entryPos < startPos`：`DiskSnapshot.skipPreDrained:189-192` 与 `SpillFileReader.recoveryAlreadyDone:198-203` 用同一 `(segmentIndex, offset)` 字典序判定，逻辑对称；`SpillFile.snapshot:371-373` 在 lock 内做 entries shallow copy 保证 startPos 与 entries 是同一物理瞬间。
- 异步 demux：`ChannelStateWriterImpl.addInputDataFromSpill:259-261` 仅 enqueue `CheckpointInProgressRequest`，真正 `writeInputFromSpill` 在 `ChannelStateWriteRequestExecutorImpl.loop:162-196` 的独立线程被 `dispatcher.dispatch` 调用，不依赖 task thread。
- writer-side 失败可达 future：`ChannelStateCheckpointWriter.runWithChecks:312-322` 捕获异常后 `fail(e)` → `failResultAndCloseStream` → 每个 `pendingResult.fail(e)`，下游 `getAndRemoveWriteResult(cpId).getInputChannelStateHandles()` future 异常完成。
- 空 snap 短路：`ChannelStateWriterImpl.addInputDataFromSpill:245-256` 在 `!chunks.hasNext()` 时 inline `chunks.close()` 并 return，不进 enqueue（`ChannelStateWriterImplAddInputDataFromSpillTest:82-108` 验证 submitCount 不增加）。
- on-disk 格式与 master 兼容：`writeInputFromSpill:190-191` 写 `[writeInt(length)][bytes]`，与 `ChannelStateSerializerImpl.writeData:160-166` 一致；`extractByOffsets:212-224` 按"offset 指向 length 前缀"读，`offset = checkpointStream.getPos()` 在写入前取（`ChannelStateCheckpointWriter.java:189`）与 master `write` 方法（`:233`）一致 —— 与 Step 2 的 `addInputData` 共存于同一 per-channel offsets 流，读出来仍正确。
- grant 释放全路径覆盖：(a) 成功 `writeInputFromSpill:199-201` finally close；(b) abort/cancel 经 `replayInputDataFromSpill:280` 的 `throwable -> chunks.close()` discardAction，由 `CheckpointInProgressRequest.cancel:379-383` 触发；(c) submit 失败 `ChannelStateWriterImpl.enqueue:322-330` catch 中 `request.cancel(e)` → 同 discardAction；(d) writer 已 done 时 `writeInputFromSpill:174-180` inline close；(e) 调度器同步异常 `ChannelState.onCheckpointStartedForAllInputs:172-183` finally close。`DiskSnapshot.close:167-176` 自身幂等（`closed` 守护），多路径重复 close 安全。

## 不符合预期

- `flink-runtime/src/main/java/org/apache/flink/runtime/checkpoint/channel/ChannelStateWriter.java:248-251`：`NO_OP.addInputDataFromSpill` 内 `catch (Exception ignored)` 静默吞 `chunks.close()` 异常，与 G1 "fail-loud not silent" 相违；非空 snap 误送进 NO_OP 时段 grant 仍有效但异常被吞，定位困难。仅当 feature 完全关闭时 NO_OP 路径才被进入，影响面有限，但仍违反 checklist `G1`。
- `flink-runtime/src/main/java/org/apache/flink/runtime/checkpoint/channel/ChannelStateCheckpointWriter.java:174-180`：writer `isDone()` 短路分支 `try { chunks.close(); } catch (Exception ignored) {}`，同样静默吞 close 异常，定位 grant-leak 时无法看到 close 失败的根因。

## 总评

PASS WITH MINOR — F6 核心三点（按 `chunk.channelInfo` demux、字典序跳过 pre-drained、grant 全路径释放）均与设计一致，writer-side 异常通过 result future 正确暴露；唯一偏离是两处 `chunks.close()` 异常被静默吞，违反 G1（fail-loud）原则但不影响 F6 自身正确性。
