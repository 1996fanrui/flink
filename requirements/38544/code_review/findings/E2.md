# E2. recoveredBuffers 队列只装 drain buffer 和 RecoveryCheckpointBarrier

## 设计期望

- `recoveredBuffers` 仅在 recovery 期间承载内容；recovery 完成后永久空。
- 仅两类合法写入：drain phase 通过 `onRecoveredStateBuffer` 投递的 buffer（含 `RecoveredInputChannel.toInputChannel()` 迁移路径），以及 task thread Step 1 插入的 `RecoveryCheckpointBarrier` sentinel。
- `toBeConsumedBuffers` 在 `LocalInputChannel` 上只承载 `FullyFilledBuffer` splits，不能混 recovery 数据。
- FLINK-39018 历史入口（`initialRecoveredBuffers` 构造参数、`getNextRecoveredBuffer()` 独立方法、`checkpointStarted` 扫 `toBeConsumedBuffers` 取 recovery）应已退回 master 形式。

## 符合预期

- `LocalInputChannel.recoveredBuffers` 字段声明为 `Deque<Buffer>`（`LocalInputChannel.java:94`），`RemoteInputChannel.recoveredBuffers` 同型（`RemoteInputChannel.java:133`）；类型与设计一致。
- `LocalInputChannel.toBeConsumedBuffers` 退回 master 形式 `Deque<BufferAndBacklog>`（`LocalInputChannel.java:88`），通过类型系统隔离，无法承载裸 `Buffer` 的 recovery 数据；`getNextBuffer` 中 `toBeConsumedBuffers` 分支只装 `FullyFilledBuffer` splits（`LocalInputChannel.java:451-463`）。
- `LocalInputChannel` 构造函数不再接收 `ArrayDeque<Buffer> initialRecoveredBuffers`（`LocalInputChannel.java:124-151`）；全仓 `grep initialRecoveredBuffers` / `getNextRecoveredBuffer` 在 `flink-runtime/src/main/java/` 下无任何命中，FLINK-39018 入口完全删除。
- 仅 `onRecoveredStateBuffer` 是 `recoveredBuffers` 的唯一写入点（`LocalInputChannel.java:176`、`RemoteInputChannel.java:234`），全仓只此两处 `recoveredBuffers.add`。
- `LocalInputChannel.checkpointStarted` not-in-recovery 分支退回 master `Collections.emptyList()` 喂 `startPersisting`（`LocalInputChannel.java:213-218`），不再扫 `toBeConsumedBuffers`；并以 `assert recoveredBuffers.isEmpty()` 防御反向越界（`LocalInputChannel.java:211`）。
- `RemoteInputChannel.checkpointStarted` not-in-recovery 分支沿用 master 既有 `getInflightBuffersUnsafe`（`RemoteInputChannel.java:880`），且以 `assert recoveredBuffers.isEmpty()` 防御（`RemoteInputChannel.java:869`）。
- `releaseAllResources` 单独清空 `recoveredBuffers` 与 `toBeConsumedBuffers`（`LocalInputChannel.java:675-685`、`RemoteInputChannel.java:489-492`），两队列生命周期保持隔离。
- `RecoveredInputChannel.toInputChannel` 通过统一 `RecoverableInputChannel` 接口迁移残余 buffer（`RecoveredInputChannel.java:136-146`），落点也是新 `recoveredBuffers`，与 drain 走同一入口；不会绕进 `toBeConsumedBuffers`。
- `RecoveryCheckpointBarrier` 仅由 `SpillFileReader` Step 1 注入（`SpillFileReader.java:167`），channel 侧 `collectPreRecoveryBarrier` 通过事件反序列化识别并 `it.remove()`（`LocalInputChannel.java:238-253`、`RemoteInputChannel.java:903-919`），不会泄漏到 operator。

## 不符合预期

无（仅一条提示项，不影响 E2 判定）。

- `LocalInputChannel.java:702-704,711` / `LocalInputChannel.java:702-714`：`getBuffersInUseCount` / `unsynchronizedGetNumberOfQueuedBuffers` 读取 `recoveredBuffers.size()` 未持有 `synchronized(recoveredBuffers)` 监视器。仅是计数读，不影响 "队列只装两类内容" 的不变量；属于 E3（锁复用 + 锁顺序）范畴，E2 不计入失败。

## 总评

PASS — `recoveredBuffers` 写入面收敛到唯一入口 `onRecoveredStateBuffer`，`toBeConsumedBuffers` 类型回退 master 形式且仅承载 `FullyFilledBuffer` splits，FLINK-39018 历史耦合已完全清除，两队列职责互斥且通过 defensive assert 保护。
