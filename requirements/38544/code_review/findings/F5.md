# F5. RecoveryCheckpointBarrier sentinel 不泄漏

## 设计期望

- 仅 task thread 在 Step 1 插入 `RecoveryCheckpointBarrier` 到每个 channel 的 `recoveredBuffers`；仅 task thread 在 Step 2 通过 `it.remove()` 真正移除（不仅 `break`）。
- operator/network/deser/operator chain 永不出现 `instanceof RecoveryCheckpointBarrier`。
- sentinel `isBuffer() == false`（event buffer，非 data buffer），避免被 deserializer 当作 byte 流处理。
- sentinel 携带 `getCheckpointId()`，跨 cpId barrier 按 cpId 匹配，互不影响。

## 符合预期

- `RecoveryCheckpointBarrier extends RuntimeEvent`，带 `getCheckpointId()` + `equals/hashCode` 按 cpId 区分（`RecoveryCheckpointBarrier.java:48`/`63-72`），跨 cpId 互不混淆。
- 插入唯一点：`SpillFileReader.snapshotAndInsertBarriers` lock 内对每个 `allChannels` 调 `onRecoveredStateBuffer(EventSerializer.toBuffer(new RecoveryCheckpointBarrier(checkpointId), false))`（`SpillFileReader.java:163-168`）；`hasPriority=false` → `EVENT_BUFFER`（`Buffer.java:289`、`408`），`isBuffer()` 为 `false`。
- 移除位置严格落在 Step 2：`LocalInputChannel.collectPreRecoveryBarrier` `it.remove(); b.recycleBuffer(); return retained;`（`LocalInputChannel.java:243-246`），`RemoteInputChannel.collectPreRecoveryBarrier` 同形（`RemoteInputChannel.java:909-912`）—— 真 `it.remove()`，不是仅 `break`。
- cpId 匹配过滤：`isRecoveryCheckpointBarrier` 用 `((RecoveryCheckpointBarrier) event).getCheckpointId() == checkpointId` 判定（`LocalInputChannel.java:263-264`、`RemoteInputChannel.java:929-930`），并先 `b.isBuffer()` 短路过滤，避免对 data buffer 误调 `EventSerializer.fromBuffer`。
- `isRecoveryCheckpointBarrier` 反序列化后 `b.setReaderIndex(0)`（`LocalInputChannel.java:262`、`RemoteInputChannel.java:928`）—— 哪怕该 buffer 不是当前 cpId 的 barrier，readerIndex 也复位回去，不影响后续真正消费它的人。
- operator/network/deser path 不存在任何对 `RecoveryCheckpointBarrier` 的 `instanceof`：全量 grep 仅命中 Step 1 插入 (`SpillFileReader.java:167`) 与 Step 2 walker (`LocalInputChannel.java:263`、`RemoteInputChannel.java:929`)；`flink-streaming-java/src/main/java` 全无引用。
- Step 1 仅由 task thread 在 `ChannelState.onCheckpointStartedForAllInputs` 调度（`ChannelState.java:163`），不存在第二个插入入口。
- drain 阶段 `SpillFileReader.allChannels` 是物理 `LocalInputChannel` / `RemoteInputChannel`（构造时机已过 conversion），Step 1 不会向 `RecoveredInputChannel` 插入 sentinel；`RecoveredInputChannel.toInputChannel()` 迁移 `receivedBuffers` 时只搬运既有 buffer（`RecoveredInputChannel.java:124-141`），不会引入 sentinel。

## 不符合预期

- `flink-runtime/src/main/java/org/apache/flink/streaming/runtime/io/checkpointing/ChannelState.java:165-167`：Step 1 已对所有 channel 插入 sentinel，但 Step 2 在 `for (CheckpointableInput input : inputs)` 内调用 `input.checkpointStarted(barrier)` 若某 channel 抛 `CheckpointException` 即中断循环，循环之后的 channel 的 sentinel 留在 `recoveredBuffers`，违反"Step 1 插入 + Step 2 remove"对称性。
- `flink-runtime/src/main/java/org/apache/flink/runtime/io/network/partition/consumer/LocalInputChannel.java:400`：`buf = recoveredBuffers.poll();` 无 `isRecoveryCheckpointBarrier` 防御，残留 sentinel 会被消费者 poll 出 → 经 `wrapRecoveredBufferAsAvailability` → `SingleInputGate.transformEvent`（`SingleInputGate.java:1101`）反序列化为 `RecoveryCheckpointBarrier`，沿 `CheckpointedInputGate.handleEvent` → `AbstractStreamTaskNetworkInput.processEvent` 一路下行无任何分支识别，被静默丢弃，违反"operator 永不看见"。
- `flink-runtime/src/main/java/org/apache/flink/runtime/io/network/partition/consumer/RemoteInputChannel.java:356`：`Buffer buf = recoveredBuffers.poll();` 同上，残留 sentinel 会被消费者拿到并经 `SingleInputGate.transformEvent` 反序列化为事件后静默漏出。
- `flink-runtime/src/main/java/org/apache/flink/runtime/io/network/partition/consumer/LocalInputChannel.java:530`、`flink-runtime/src/main/java/org/apache/flink/runtime/io/network/partition/consumer/RemoteInputChannel.java:358-359`：当 `recoveredBuffers` 头部是 sentinel 时 `peek().getDataType()` 会汇报 `EVENT_BUFFER` 作为 `nextDataType`，下游 availability/priority 判断会被 sentinel 这一非业务事件污染（属同一根因：消费者侧未对 sentinel 做识别/过滤）。

## 总评

FAIL — Step 1 / Step 2 自身的插入与匹配语义正确，但 Step 2 多 channel 异常中断后残留 sentinel 没有兜底过滤，`getNextBuffer` 直接将 sentinel 透传到下游 deser 路径，违反 F5 "operator 看不到 + 仅 Step 1/Step 2 出现"的核心约束。
