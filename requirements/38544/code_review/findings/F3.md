# F3. checkpointStarted 互斥分支（in-recovery vs not-in-recovery）

## 设计期望
- `channel.checkpointStarted(barrier)` 在 channel-internal monitor 内根据 `inRecovery = !allRecoveredBuffersDelivered || !recoveredBuffers.isEmpty()` 走 if/else **互斥**两分支，不允许两分支同时执行任何一部分。
- in-recovery 分支：先 defensive 校验 `receivedBuffersHasNoLiveDataBuffer()`（Remote）或 `recoveredBuffers` 上下文（Local 因无 `receivedBuffers` 字段语义上 trivially true），然后遍历 `recoveredBuffers`，遇到 cpId 匹配的 `RecoveryCheckpointBarrier` 时 `it.remove()` + 终止；遍历过程中 `b.retainBuffer()` 把 pre-barrier **data** buffer 交给 channel-state writer。
- not-in-recovery 分支：保持 master 原行为 —— Remote 走既有 `lastBarrierId` 校验 + `getInflightBuffersUnsafe`；Local 由于 master 既无 `receivedBuffers` 也不持 inflight 数据，走 `Collections.emptyList()` 退回 pre-FLINK-39018 形状。
- 进入互斥分支的 monitor：Remote `synchronized(receivedBuffers)`，Local `synchronized(recoveredBuffers)`（与 `onRecoveredStateBuffer`、`getNextBuffer`、`finishReadRecoveredState` 一致，无第三把锁）。

## 符合预期
- 两分支结构以单 `if (inRecovery) { ... } else { ... }` 互斥落地：Remote `RemoteInputChannel.java:858-881`、Local `LocalInputChannel.java:205-214`；`else` 内无任何 in-recovery 代码，`if` 内也无 master inflight 逻辑，互斥成立。
- `inRecovery` 表达式两端使用同一形式 `!allRecoveredBuffersDelivered || !recoveredBuffers.isEmpty()`（Remote `RemoteInputChannel.java:858`、Local `LocalInputChannel.java:205`），并与 `getNextBuffer`（`RemoteInputChannel.java:338`、`LocalInputChannel.java:386`）/ `checkReadability`（`RemoteInputChannel.java:1125`）保持一致。
- in-recovery 分支正确 retain pre-barrier data buffer 并在命中 barrier 时 `it.remove()` + `recycleBuffer()`：Remote `RemoteInputChannel.java:904-918`、Local `LocalInputChannel.java:239-252`；retained list 通过 `channelStatePersister.startPersisting(barrierId, toPersist)` 交给 writer（最终走 `channelStateWriter.addInputData` + `CloseableIterator.fromList(..., Buffer::recycleBuffer)`，见 `ChannelStatePersister.java:93-99`），retain/release 配对正确。
- defensive 校验落地：Remote 在 in-recovery 分支顶部 `assert receivedBuffersHasNoLiveDataBuffer()`（`RemoteInputChannel.java:863-864`），实现遍历 `receivedBuffers` 中每个 `SequenceBuffer.buffer.isBuffer()`（`RemoteInputChannel.java:937-947`）—— 包含 priority 段（PrioritizedDeque.iterator 覆盖全部元素，priority 元素都是 events，`!isBuffer()` 判定为真）；Local 无 `receivedBuffers` 字段、live data 走 `subpartitionView`，仅 priority-event 通过 §3.6 路径，trivially 满足，因此 Local 未写显式 helper 与设计 §3.3 一致。
- not-in-recovery 分支对 Remote 保持 master 行为：`RemoteInputChannel.java:871-881` 与 master 既有版（`git show master:.../RemoteInputChannel.java:690-710`）逐行一致（仅多了 `toPersist` 变量提取），`lastBarrierId` 检查 + `getInflightBuffersUnsafe(barrier.getId())` 都未被改写。
- not-in-recovery 分支对 Local 回到 pre-39018 形状：`LocalInputChannel.java:213` 使用 `Collections.emptyList()`，没有扫 `toBeConsumedBuffers` 取 recovery 残留（FLINK-39018 commit `3aef0932ded` 的扫描点已被移除），与 input_channel.md §3.5 的 revert 表一致。
- 互斥的 else 分支再加上 `assert recoveredBuffers.isEmpty()`（Remote `RemoteInputChannel.java:869-870`、Local `LocalInputChannel.java:211-212`），fail-fast 守住 §3.3 的 temporal 互斥不变式。
- Monitor 选取符合 §3.3 / input_channel.md §3.3：Remote 整体 `synchronized (receivedBuffers)`（`RemoteInputChannel.java:857`），Local 整体 `synchronized (recoveredBuffers)`（`LocalInputChannel.java:204`），与 `onRecoveredStateBuffer` / `finishReadRecoveredState` / `getNextBuffer` 复用同一把锁，未引入第三把锁。
- `RecoveredInputChannel.checkpointStarted` 仍是 master 既有的 `CHECKPOINT_DECLINED_TASK_NOT_READY`（`RecoveredInputChannel.java:356-358`），filter 阶段不允许 checkpoint 落地到 recovered 通道本身，与 F3 互斥前提（filter→conversion→drain 串行后才走 3-step）一致。

## 不符合预期
- `RemoteInputChannel.java:939` 内联注释 "Skip priority elements at the head; check all remaining elements." 与紧随其后的 `Iterator<SequenceBuffer> it = receivedBuffers.iterator();` while-loop 行为不一致：循环实际遍历 priority + non-priority 全部元素，并未跳过 priority；幸而 priority 元素都是 events（`!isBuffer()`）所以语义结果正确，仅注释误导后续阅读者。属注释 bug，不影响互斥分支正确性。
- `LocalInputChannel.java:205-214` in-recovery 分支没有等价的 `receivedBuffersHasNoLiveDataBuffer` 调用或显式注释说明 trivially-true 的来源；设计 input_channel.md §3.3 / coordination.md §3.3 已声明 Local trivially 成立，但代码层缺少一行 inline 注释，未来若 Local 拓展 receivedBuffers 语义时容易漏防。属可读性观察，不阻塞 F3。

## 总评
PASS WITH MINOR — 互斥分支结构、retain/remove、monitor 选取、master not-in-recovery 路径回归全部落地；仅 `receivedBuffersHasNoLiveDataBuffer` 上方注释与实际行为不符（事实上覆盖更广），以及 Local 缺一行 trivially-true 解释，均为非阻塞的注释/可读性级别瑕疵。
