# E5. inRecovery 判定 + getNextBuffer 双路径

## 设计期望

- `inRecovery = !allRecoveredBuffersDelivered || !recoveredBuffers.isEmpty()`，两个物理 channel 必须使用同一表达式；`getNextBuffer` 与 `checkpointStarted` 两个入口对该 predicate 的判定保持一致（最好抽 helper）。
- 不允许只判 `recoveredBuffers.isEmpty()` 或只判 `!allRecoveredBuffersDelivered`，否则漏 boundary（4 种边界：未产/产中/产完未消/产完消完）。
- in-recovery 期间 `getNextBuffer`：先看 priority event（Remote 经 `receivedBuffers.getNumPriorityElements()` 后 `pollReceivedBufferAsPriority`，Local 经 `subpartitionView` priority 入口 `pullPriorityFromSubpartitionView`），普通 upstream data 必须屏蔽；其次从 `recoveredBuffers.poll()` 取一条；都没有则返回 `Optional.empty()`。
- not-in-recovery 走 master 路径：Remote 走原 `receivedBuffers` 路径；Local 走 `toBeConsumedBuffers`/`subpartitionView` 原路径。
- 返回 empty 时不破坏 wake-up：依赖 `onRecoveredStateBuffer` 内 `wasEmpty` 时调 `notifyChannelNonEmpty()`、以及上游 priority 走 `notifyPriorityEvent` 链。
- `inRecovery` 读取必须在 channel monitor（Remote `receivedBuffers`、Local `recoveredBuffers`）内进行。

## 符合预期

- 两个 channel 上 `inRecovery` 表达式与设计完全一致：`!allRecoveredBuffersDelivered || !recoveredBuffers.isEmpty()`（`RemoteInputChannel.java:338,858,1125`、`LocalInputChannel.java:205,386`）。无任何半 predicate（"只判 isEmpty" 或 "只判 flag"）的退化形式。
- 4 种边界覆盖：未产（`!flag, empty` → true, 返回 Empty 等待）、产中（`!flag, !empty` → true, poll 队首）、产完未消（`flag, !empty` → true, poll 队首）、消完（`flag, empty` → false, 走 master），逻辑闭合。
- `inRecovery` 读取均在 channel monitor 内：Remote 在 `synchronized (receivedBuffers)`（`RemoteInputChannel.java:337,857,1124`，后者带 `assert Thread.holdsLock`），Local 在 `synchronized (recoveredBuffers)`（`LocalInputChannel.java:385,394,204`），符合 §3.3 复用 monitor 的设计。
- Remote 双路径：in-recovery 分支先 `getNumPriorityElements() > 0` → `pollReceivedBufferAsPriority`（`RemoteInputChannel.java:345-346,418-451`），否则 `recoveredBuffers.poll()`（`RemoteInputChannel.java:348-376`）；not-in-recovery 走 master `receivedBuffers` 路径（`RemoteInputChannel.java:379-415`），分支严格互斥。
- Local 双路径：in-recovery 分支先 `hasPendingPriorityEvent` → `pullPriorityFromSubpartitionView`（`LocalInputChannel.java:390-392,474-503`），否则 `recoveredBuffers.poll()`（`LocalInputChannel.java:393-402`）；not-in-recovery 走 `toBeConsumedBuffers` 与 `subpartitionView` 原路径（`LocalInputChannel.java:405-466`），符合 §3.6 双路径形态。
- Remote priority polling 借助 PrioritizedDeque 的不变式（priority 元素恒在队首，`PrioritizedDeque.java:59-79`）保证 `numPriorityElements > 0` 时 `poll()` 返回的就是 priority 元素；`poll()` 同时维护 `numPriorityElements` 计数（`PrioritizedDeque.java:174-180`）。
- 普通 upstream data 在 recovery 期间被有效屏蔽：Remote 仅在 `numPriorityElements > 0` 才触碰 `receivedBuffers`，否则不读；Local 完全不调 `subpartitionView.getNextBuffer()`，只走 `pullPriorityFromSubpartitionView`（其内部 `checkState` 强校验 priority dataType，`LocalInputChannel.java:477-480`）。
- 返回 Empty 时上层 wake-up 链未断：`onRecoveredStateBuffer` 在 `wasEmpty` 时调 `notifyChannelNonEmpty()`（Remote `RemoteInputChannel.java:236-238`、Local `LocalInputChannel.java:178-180`），priority event 经 `notifyPriorityEvent` 链（Local `LocalInputChannel.java:596-601`），均保证下一条 buffer / priority 到达时 gate 重新可读。
- recovery → not-in-recovery 过渡正确：消完最后一条时，`wrapRecoveredBufferAsAvailability` 探测 `subpartitionView.getAvailabilityAndBacklog(true)` 把 `nextDataType` 设为真实下一类型（`LocalInputChannel.java:528-547`）；Remote 通过 nextDataType 计算 fallback 到 `receivedBuffers.peek()`（`RemoteInputChannel.java:357-364`），下一次 `getNextBuffer` 自然走 master 分支。

## 不符合预期

- `RemoteInputChannel.java:336-377`：`getNextBuffer` 的 in-recovery 路径在第 337 行计算 `inRecovery` 后释放 monitor，再于第 344 行重新进入 `synchronized (receivedBuffers)`，predicate 的「判断」与「使用」跨锁。若 `finishReadRecoveredState` 在两段 sync block 之间翻转 flag（drain 此时已不再写入 `recoveredBuffers`，符合 end-of-drain 例外），第二段 sync block 内仍然按 in-recovery 分支处理，会返回一次「spurious empty」。该一次 spurious empty 是良性的（下次 `getNextBuffer` 会按 `inRecovery=false` 走 master），不破坏正确性，但违反了 checklist「inRecovery 读取应在同一 monitor 内一气呵成」的约束（Local 同样的 `getNextBuffer` 同样跨两段 sync block：`LocalInputChannel.java:384-401`）。
- `RemoteInputChannel.java:338,858,1125` 与 `LocalInputChannel.java:205,386`：`inRecovery` 表达式在 5 处硬编码重复，未抽取 helper（如 `@GuardedBy boolean inRecovery()`），违反 checklist「最好抽 helper」的建议；属于可维护性瑕疵，未来若 predicate 演化需要同步多处。
- `LocalInputChannel.java:395-399`：in-recovery 分支返回 Empty 时未做 `isReleased` 检查，而 Remote 对应分支（`RemoteInputChannel.java:350-353`）会在 `isReleased.get()` 时抛 `CancelTaskException`。两个 channel 的「释放后查询」语义存在不一致，Local 这一支静默返回 Empty 可能掩盖 task cancel 时的 buffer-poll 错乱。

## 总评

PASS WITH MINOR — 两个 channel 的 `inRecovery` 表达式、4 种边界、in-recovery 期间 priority 优先 / 普通 data 屏蔽 / 返回 Empty wakeup 链、not-in-recovery 走 master 路径均符合设计；瑕疵限于 helper 未抽、predicate 跨锁读取一次性 spurious empty、以及 Local in-recovery 分支 `isReleased` 未与 Remote 对齐，均不影响正确性。
