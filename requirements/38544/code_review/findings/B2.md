# B2. SpillFile.close() 是 forced cleanup（production 禁用）

## 设计期望

`SpillFile.close()` 是绕过 refCount 的强制清理入口，仅保留给 test tearDown / task-manager shutdown 兜底；production filter→drain 主路径必须走 `acquire()/release()` 引用计数语义，**绝不**调用 `close()`。`FilteredBufferWriter.close()` / `SpillFileWriter.close()` 只允许 flush 或 `release()`，不允许 `close()`。forced close 必须能容忍 ref 未归零，且通过 CAS 保证 `deleteAllSegments` 不重复执行。

- `flink-runtime/src/main/java/org/apache/flink/runtime/checkpoint/channel/SpillFile.java:285-340`（`release()` / `close()` / `deleteAllSegments`）
- `flink-runtime/src/main/java/org/apache/flink/runtime/checkpoint/channel/SpillFile.java:169-176`（`refCount` / `cleanedUp` 字段）
- `flink-runtime/src/main/java/org/apache/flink/runtime/checkpoint/channel/SpillFileWriter.java:58-73`（`close()`）
- `flink-runtime/src/main/java/org/apache/flink/runtime/checkpoint/channel/FilteredBufferWriter.java:122-135`（`close()`）
- `flink-runtime/src/main/java/org/apache/flink/runtime/checkpoint/channel/SpillFileReader.java:180-187`（`close()`）

## 符合预期

- `SpillFile.close()` 实现 (`SpillFile.java:300-309`) 是 forced cleanup：`closed` 早返保证幂等；`cleanedUp.compareAndSet(false,true)` 与 `release()` (`SpillFile.java:286-291`) 共享同一 CAS，`deleteAllSegments` 至多执行一次，满足"容忍 ref 未归零 + 不重复删除"语义。
- production 代码全文 grep `SpillFile.*\.close()` / `spillFile.close()` 在 main 源码中无任何匹配，仅在 test 中出现（`SpillFileTest.java:100,152,155` / `SpillFileRefCountTest.java:118,122` / `ChannelIOExecutorDrainSubmissionTest.java:101,160` / `SpillFileReaderConcurrencyTest.java:166`）。production filter→drain 全部使用 `acquire()/release()`。
- `SpillFileWriter.close()` (`SpillFileWriter.java:67-73`) 只 `accumulator.close()`，不触碰 `SpillFile` 生命周期；javadoc (`SpillFileWriter.java:58-65`) 明确"Does not touch the SpillFile lifecycle"，并解释 producer grant 必须 outlive 此 close。
- `FilteredBufferWriter.close()` (`FilteredBufferWriter.java:128-135`) 只调 `flush()`，明确不接触 `SpillFile`（`FilteredBufferWriter.java:122-127` javadoc）。
- `SpillFileReader.close()` (`SpillFileReader.java:181-187`) 通过 `spillFile.release()` 释放 drain 持有的 grant，**未**调用 `close()`。
- `DiskSnapshot.close()` (`DiskSnapshot.java:167-176`) 同样使用 `spillFile.release()`，每个 cpId reader 走引用计数。
- `RecoveredChannelStateHandler.close()` (`RecoveredChannelStateHandler.java:351-358`) 仅 `spillFileWriter.close()`；producer grant 通过 `StreamTask.handoffSpillReaderToDrain` finally (`StreamTask.java:1095-1103`) 释放。
- `StreamTask.java:923-936, 1015-1031` 异常路径（filter 抛 / 转换抛）走 `leakedSpillFile.release()`，不是 `close()`，与设计一致。
- `SpillFile.close()` javadoc (`SpillFile.java:294-299`) 明确标注"Forced cleanup entry retained for tests and task-manager shutdown"，符合设计文档 [`unspiller.md`](../simplify_approach/unspiller.md) §2a 的描述。

## 不符合预期

无。

## 总评

PASS — `SpillFile.close()` 在 production 路径无任何调用，所有 happy/失败/异常路径都走 `release()`；`close()` 自身共享 `cleanedUp` CAS 保证幂等并能容忍未归零 refCount，与设计完全吻合。
