# F2. 调度器内部顺序 + no-op 收敛（无外层 if filter-on）

## 设计期望
- 调度器 `ChannelState.onCheckpointStartedForAllInputs` 内部线性顺序：(Step 1) `recoveryCheckpointTrigger.snapshotAndInsertBarriers(cpId)` → (master per-input 循环) `for (input : inputs) input.checkpointStarted(barrier)`（Step 2 已下沉到 channel 内部互斥分支）→ (Step 3) `channelStateWriter.addInputDataFromSpill(cpId, snap)`。
- 调度器层禁止出现 `if (filterEnabled)` / `if (recoveryCheckpointTrigger != null)` 等外层 guard；feature-off 与 recovery 全部完成均通过 null-object 收敛：
  - `RecoveryCheckpointTrigger.NO_OP` 返回 `DiskSnapshot.empty()`，不动 channel。
  - `ChannelStateWriter.NO_OP.addInputDataFromSpill` no-op；实操 writer 端识别空 snap → 不下发 demux。
- 调度器禁止自写 Step 2 outer loop（Step 2 嵌入 `channel.checkpointStarted`）。

## 符合预期
- 调度器线性顺序严格按 1 → 2 → 3 落地：`ChannelState.java:163` 调用 `snapshotAndInsertBarriers(cpId)`，`ChannelState.java:165-167` 是 master 既有 per-input 迭代 `input.checkpointStarted(barrier)`，`ChannelState.java:169` 调用 `addInputDataFromSpill(cpId, snap)`；调度器内没有自行实现 Step 2 walk。
- 调度器无外层 feature guard：`ChannelState.java:158-184` 中无 `if (filterEnabled)` / `if (recoveryCheckpointTrigger != null)` 判断；`recoveryCheckpointTrigger` / `channelStateWriter` 字段通过构造器 `checkNotNull`（`ChannelState.java:85-86`）保证总是非 null。
- Trigger null-object 路径合规：`RecoveryCheckpointTrigger.NO_OP`（`RecoveryCheckpointTrigger.java:63`）直接返回 `DiskSnapshot.empty()`，单 arg 构造器（`ChannelState.java:76-78`）和 `InputProcessorUtil.java:104` 的 supplier 默认值都收敛到 `NO_OP`。
- Writer null-object 路径合规：`ChannelStateWriter.NO_OP.addInputDataFromSpill`（`ChannelStateWriter.java:246-252`）仅关闭 iterator；实操 `ChannelStateWriterImpl.addInputDataFromSpill`（`ChannelStateWriterImpl.java:245-256`）对 `!chunks.hasNext()` 早 return + 关 iterator，不提交 writer 异步任务。
- 真正运行时的空 snap 收敛：`SpillFileReader.snapshotAndInsertBarriers`（`SpillFileReader.java:142-173`）在 `recoveryAlreadyDone(...)` 为真时直接返回 `DiskSnapshot.empty()` 且不插 barrier、不 `acquire()`；非空时按 `(currentSegmentIndex, currentOffset)` 拍 `StartPos` 并对全部 channel 插入 `RecoveryCheckpointBarrier`，行为与设计 §3.4 一致。
- 仅在两个 UC 入口调用调度器：`AlternatingWaitingForFirstBarrierUnaligned.java:78`、`AlternatingCollectingBarriers.java:49`；aligned 路径（`AlternatingCollectingBarriers.endOfPartitionReceived` line 64-67 断言 `!isUnalignedCheckpoint()`）不调度，`WaitingForFirstBarrier.java:30` 单 arg ChannelState 也走 NO_OP，符合 F2 与 F1 的协同约束。
- 同步异常路径 grant 不泄漏：`ChannelState.java:172-183` finally 中如果 snap 未交付 writer 则调用 `snap.close()`，`DiskSnapshot.close()`（`DiskSnapshot.java:168-176`）idempotent 释放 `SpillFile` ref-count。
- 测试覆盖：`ChannelStateDispatcherTest.java:76-79, 95-100` 用 trace 锁定 trigger → per-input checkpointStarted → writer 三步顺序，并验证 feature-off 时 writer 端识别空 snap no-op。

## 不符合预期
（无；以下为非阻塞的轻微观察）
- `ChannelState.java:146` doc 字符串称 Step 2 是 "master's existing per-input iteration of `checkpointStarted(barrier)`"；但 master 中此循环过去内嵌在两个 `Alternating*` 状态里，这里被搬到 `ChannelState` 后描述为 "master existing" 略带歧义。文字层面，不影响行为正确性。

## 总评
PASS — 调度器线性顺序、no-op 收敛与"无外层 if filter-on"三项要求在 `ChannelState.onCheckpointStartedForAllInputs` + 两个 NO_OP null-object 上都已严格落地。
