# B1. SpillFile 引用计数 + 生命周期 — Review Findings

## 设计期望

- `SpillFile.refCount` 由三个 holder 各持一份：producer (filter 管线)、drain (SpillFileReader)、每个 in-recovery cpId 的 Step 3 reader (DiskSnapshot)。
- Producer 持初始 grant，直到 drain reader 接手后才释放 —— 不允许出现 refCount = 0 的窗口。
- 失败路径（filter throws / conversion throws / buildReader throws）producer grant 都必须显式释放。
- Step 3 reader 的 grant 挂在 writer success / abort 两条回调上各释放一次（DiskSnapshot.close 幂等）。
- `deleteAllSegments` 通过 `cleanedUp` CAS 保证最多执行一次；release 归零和 close 强制清理共用同一个 CAS。
- `SpillFile.close()` 仅作为 forced cleanup（test/shutdown），production filter→drain 路径不调用。

## 符合预期

- 3 个 acquire 与 5 个 release 调用点完整配对（producer / drain / Step 3 reader 各 1 acquire；release 在 success/abort/3 个失败路径上分布）。
- `SpillFile.release()` 归零后通过 `cleanedUp.compareAndSet(false, true)` 守护 `deleteAllSegments`，与 forced `close()` 共用 CAS（SpillFile.java:286-292, 300-309）。
- Producer 持 initial grant 在 handler `ensureSpillFileWriter` 取得（RecoveredChannelStateHandler.java:294），在 `handoffSpillReaderToDrain` finally 释放（StreamTask.java:1095-1103），中间 reader 构造期 acquire（SpillFileReader.java:88）—— 设计中的 hand-off 窗口被 producer grant 撑住。
- buildReader 抛错的失败路径走 handoff finally 释放 producer grant；SpillFileReader 构造里 `spillFile.acquire()` 是末尾一行，没有 acquired-then-throw 风险（SpillFileReader.java:75-89）。
- Step 3 reader grant：success 路径在 `ChannelStateCheckpointWriter.writeInputFromSpill` finally close（ChannelStateCheckpointWriter.java:199-201）；abort 路径在 `CheckpointInProgressRequest.cancel` -> discardAction -> chunks.close（ChannelStateWriteRequest.java:280, 379-383）；空 snapshot 在 writer 入口早 close（ChannelStateWriterImpl.java:245-256）；DiskSnapshot.close 幂等。
- `recoveryAlreadyDone` 分支返回 `DiskSnapshot.empty()` 且不 acquire（SpillFileReader.java:156-158），与 EMPTY_INSTANCE 的 no-op close 一致。
- `SpillFile.close()` 在 production filter→drain 链路上没有任何调用点（grep 仅命中注释 SpillFile.java:132）；SpillFileWriter.close / FilteredBufferWriter.close 都只 flush，没有触碰 SpillFile lifecycle。

## 不符合预期

- `flink-runtime/.../checkpoint/channel/SequentialChannelStateReaderImpl.java:91-114`：`read()` 在 inner try 抛错时，inner finally 跑 `stateHandler.close()`（会进入 `RecoveredChannelStateHandler.close` line 351-358 并把 `handler.producedSpillFile` 设上），但**外层** `this.producedSpillFile = stateHandler.getProducedSpillFile();`（line 113）位于 inner try/finally 之外、在异常向上抛之前被跳过。结果：`SequentialChannelStateReaderImpl.producedSpillFile` 仍为 null。
- 上述 null 在两个失败路径同时失效：
  - `StreamTask.java:928` 的 `reader.getProducedSpillFile()` 返回 null，runnable 的 catch（filter throws）跳过 producer grant release（line 929-931）。
  - `StreamTask.java:1023` 的 `reader.getProducedSpillFile()` 同样返回 null，conversion 失败分支也跳过 release（line 1024-1026）。
- 净效果：filter 抛错路径上，`RecoveredChannelStateHandler.ensureSpillFileWriter` 在 line 294 已 `spillFile.acquire()`，但**没有任何后续 release** —— refCount 永远停在 1（drain reader 没构造，Step 3 reader 也没构造），segments 永久不被 `deleteAllSegments` 删除。这是 B1 "失败路径 producer release：filter throws / conversion throws / buildReader throws 每条都得有" 中 filter throws 一条的真实 leak。
- 与 checklist 的偏离：B1 要求"producer acquire 在 `RecoveredChannelStateHandler.ensureSpillFileWriter`；release 在 `StreamTask.handoffSpillReaderToDrain` finally" + filter throws 路径必须释放，当前代码只能在 happy path 上释放，filter 抛错路径上的释放逻辑因 `producedSpillFile` 上抛缺口而失效。

## 总评

FAIL — Filter 抛错的失败路径上 producer-side SpillFile grant 会真实泄漏（`SequentialChannelStateReaderImpl.producedSpillFile` 的赋值位于异常传播之外，导致 `reader.getProducedSpillFile()` 返回 null，runnable catch 中的 release 调用被静默跳过），违反 B1 "失败路径 producer release 每条都得有"。
