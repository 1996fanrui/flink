# D2. drainHandoff 在所有路径必须 complete

## 设计期望

`drainHandoff` 在 recovery + filter 路径上是 `channelIOExecutor` runnable 等待 `SpillFileReader` 构造结果的唯一汇合点（runnable 在 `drainHandoff.get()` 处阻塞）。设计要求每条可达的退出路径都必须显式 complete 该 future（`complete(reader)` / `complete(null)` / `completeExceptionally(t)`），否则 I/O 线程 hang，drain 永不启动，`stateConsumedFuture` 永不完成，下游任务 hang。具体退出路径覆盖：
- 正常 handoff：`complete(spillReader)` 或 `complete(null)`（无 spillFile）
- handoff 内 catch：`completeExceptionally(t)` + finally 释放 producer grant 两动作不能互相吞
- `allConverted.whenComplete` err 分支：`completeExceptionally(err)` + 释放 producer grant
- filter 抛异常路径（runnable catch）：`completeExceptionally(e)` + 释放 producer grant
- task cancel：显式 completeExceptionally 或依赖中断不可两条都没有

## 已 review 代码位置

- `flink-runtime/src/main/java/org/apache/flink/streaming/runtime/tasks/StreamTask.java:914-915` —— `drainHandoff` 字段构造
- `flink-runtime/src/main/java/org/apache/flink/streaming/runtime/tasks/StreamTask.java:916-969` —— `channelIOExecutor.execute` 单 runnable，含 filter catch / `drainHandoff.get()` / drain / close
- `flink-runtime/src/main/java/org/apache/flink/streaming/runtime/tasks/StreamTask.java:1009-1039` —— `allConverted.whenComplete`，含 err 分支与 mailbox 提交
- `flink-runtime/src/main/java/org/apache/flink/streaming/runtime/tasks/StreamTask.java:1065-1105` —— `handoffSpillReaderToDrain`，含正常 complete / catch / finally
- `flink-runtime/src/main/java/org/apache/flink/runtime/io/network/partition/consumer/RecoveredInputChannel.java:207-226` —— `bufferFilteringCompleteFuture` 唯一完成点（确认 cancel / Error 路径无补救）
- `flink-runtime/src/main/java/org/apache/flink/streaming/runtime/tasks/mailbox/MailboxExecutorImpl.java:70-87` —— mailbox closed 时 `execute()` 抛 `RejectedExecutionException`

## 符合预期

- `handoffSpillReaderToDrain` 三条退出路径全部覆盖：`spillFile == null` 时 `complete(null)`（StreamTask.java:1075）；构造成功时 `complete(spillReader)`（StreamTask.java:1085）；try 内抛错时 `completeExceptionally(t)`（StreamTask.java:1087）。
- handoff catch 与 finally 互不吞：catch 先 complete 再 rethrow（StreamTask.java:1087-1088），finally 独立释放 producer grant（StreamTask.java:1095-1103），两动作物理分离不会相互短路。
- `allConverted.whenComplete` err 分支（StreamTask.java:1017-1031）先 release 后 `completeExceptionally(err)`，顺序合理；release 包了 try/catch 不会吞 completeExceptionally。
- filter catch 内 `drainHandoff != null` 时执行 release + `completeExceptionally(e)`（StreamTask.java:923-936），覆盖 filter 抛 `Exception` 的常规路径。
- filter-off 路径 `drainHandoff` 为 null（StreamTask.java:914-915），runnable 在 filter 完成后 return（StreamTask.java:939-941），无需 complete。

## 不符合预期

- `StreamTask.java:921-935` —— filter catch 内 `asyncExceptionHandler.handleAsyncException(...)` 先于 release + `drainHandoff.completeExceptionally(e)` 执行；若 `handleAsyncException` 自身抛出（例如任务已 fail 后处理器路径异常），后续 release 与 completeExceptionally 全部跳过，`drainHandoff` 永久 pending。对比 `allConverted.whenComplete` err 分支（StreamTask.java:1017-1031）的顺序（先 release 再 completeExceptionally，handleAsyncException 不在该路径上），filter catch 的顺序明显更脆弱。
- `StreamTask.java:1033-1037` —— `allConverted.whenComplete` 成功分支调用 `mainMailboxExecutor.execute(...)`，依据 `MailboxExecutorImpl.java:70-87`，mailbox 关闭时该 execute 抛 `RejectedExecutionException`。该异常发生在 `whenComplete` lambda 内且未被捕获，`CompletableFuture` 会将其塞回 `allConverted` 返回的派生 future（被丢弃），导致 `drainHandoff` 既不 complete 也不 completeExceptionally，同时 producer-side SpillFile grant 也未释放。这正是 D2 列出的 "task cancel 路径：显式 completeExceptionally 或依赖中断，不能两条都没有" 防御点。
- `StreamTask.java:920` —— filter catch 仅捕获 `Exception` 不捕获 `Throwable`。若 `reader.readInputData` 抛 `Error`（如 OOM/`AssertionError`），runnable 直接退出，`drainHandoff` 永不完成；`bufferFilteringCompleteFuture` 仅在 `RecoveredInputChannel.java:222` 一处完成，filter 抛 Error 时无人推进，`allConverted` 也无法完成，因此 `whenComplete` 不会触发兜底。task cancel 仅靠 `channelIOExecutor.shutdown()`（StreamTask.java:863）按 JDK 语义不中断已运行任务，runnable 仍卡在 `drainHandoff.get()`。
- `StreamTask.java:944-947` —— `drainHandoff.get()` 捕获 `InterruptedException` 后仅设置 interrupt flag 并 `return`，但此时 `drainHandoff` 状态完全取决于 producer side：若 task cancel 由 channelIOExecutor 中断、但任务调度阶段从未触达 filter catch 或 `whenComplete`（例如 runnable 在 `readInputData` 之前已被中断），则 producer-side SpillFile grant 与 `drainHandoff` 都未被处理；checklist D2 明示 "task cancel 路径：不能两条都没有"，当前实现既无 producer-side cancel 钩子，runnable 也未在 InterruptedException 分支兜底 completeExceptionally / release。

## 总评

FAIL —— `handoffSpillReaderToDrain` 与 `allConverted.whenComplete` err 分支两路 OK，但 filter catch 顺序脆弱、`mainMailboxExecutor` mailbox-closed RejectedExecutionException 无兜底、filter 抛 `Error`/task-cancel 路径未显式 completeExceptionally 也未依赖中断，存在 D2 checklist 明确点名的退出路径漏 complete 的风险。
