# A2. FilteredBufferWriter — 一个 entry 只装一个 channel

## 设计期望

filter 阶段每条写入 spill file 的 entry 必须只对应一个 channel 的 bytes，flush 触发点只能有两个：channel 切换、buffer 满（达到 maxCapacity）。flush 之后 `currentChannel` 必须清零、size / readerIndex 归零，避免上一段 channel 信息残留污染下一段。SpillFile.append 只能由 flush 触发，不应该有第三处调用方。

## 符合预期

- `beginChannel` 在 `currentChannel != null && !currentChannel.equals(channelInfo) && outputBuffer.getSize() > 0` 时 flush，匹配触发条件 (i)（`FilteredBufferWriter.java:77-81`）。
- 首次 `beginChannel` 时 `currentChannel == null` 短路、不 flush；同一 channel 重复 `beginChannel` 也不 flush（`FilteredBufferWriter.java:77-82`）。
- `requestBufferBlocking` 在 `size == maxCapacity` 时先保存 `currentChannel`，flush 后再恢复，匹配触发条件 (ii) 且保留 channel 关联（`FilteredBufferWriter.java:97-101`）。
- `flush()` 实际写出后将 `readerIndex=0`、`size=0`、`currentChannel=null` 三处一并重置（`FilteredBufferWriter.java:117-119`）。
- `flush()` 内 `outputBuffer.getSize() == 0` 直接 return，避免对空 buffer 产生 0 长 entry（`FilteredBufferWriter.java:111-113`）；`SpillFile.append` 也做了 `length == 0` 二次保护（`SpillFile.java:209-214`）。
- 全文件 grep 确认 `spillFile.append` 在生产代码里只有一个 caller：`FilteredBufferWriter.flush()`（`SpillFile.java:201` ← `FilteredBufferWriter.java:116`），没有第三触发点。
- `SpillFile.append` 单次调用恰好生成一个 `Entry(channelInfo, segmentIndex, offset, length)` 并同时入 `entries`/`drainEntries`（`SpillFile.java:230-235`），确保 “一次 flush = 一个 entry = 一个 channel” 关系一一对应。
- `close()` 通过 `flush()` 收尾残留 bytes，残留同样按当前 `currentChannel` 落盘，不会出现混合 channel 的 entry（`FilteredBufferWriter.java:128-135`）。
- `recoverWithFiltering` 始终在调用 filter 前先 `accumulator.beginChannel(channel.getChannelInfo())`，避免 filter 在 `currentChannel == null` 状态下被允许触发 flush（`RecoveredChannelStateHandler.java:247`）。

## 不符合预期

- `FilteredBufferWriter.java:96` `requestBufferBlocking` 顶部用 `assert currentChannel != null` 守护 “必须先调用 `beginChannel`”，而 `flush()` 内 `assert currentChannel != null` 在 `:114` 同样是 assert。assertions 在生产 JVM 默认关闭，万一 filter 路径未先调 `beginChannel` 就触发 buffer-full flush，会进到 `spillFile.append(null, payload)` 路径——`SpillFile.append` 内 `checkNotNull(channelInfo)`（`SpillFile.java:206`）才会真正 fail-loud。checklist G1 要求 “设计保证必然能做到的事情，做不到必须抛”，这里把守护责任下放到 `SpillFile.append`，A2 自身缺少强制校验。属于 minor。
- `FilteredBufferWriter.java:114` `flush()` 的 `currentChannel != null` assert 同上。理论上 `getSize() > 0` 蕴含曾经写过数据，因此 `currentChannel` 必非 null；该 assert 是双保险，但未升级为 `checkState`。属于 minor。

## 总评

PASS WITH MINOR — “一个 entry 只装一个 channel” 的两条触发路径、flush 重置、单一 append caller 都符合设计；唯一两处偏差是 `currentChannel` 非空守护只用 `assert` 而非 `checkState`，生产 JVM 关 assert 时只能依赖下游 `SpillFile.append` 的 null 校验兜底，不影响一个 entry 一个 channel 的不变量本身。
